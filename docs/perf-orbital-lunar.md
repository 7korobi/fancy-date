# 創作赤星・衛星の性能測定

創作赤星とその衛星へ追加した月出・月没・南中、太陽相対朔、太陰太陽暦の性能記録。

## 測定条件

- 測定日時: 2026-08-01 00:13 JST
- CPU architecture: `arm64`
- macOS: `15.6`
- Bun: `1.2.16`
- Node.js: `v22.12.0`
- コマンド: `bun run perf:orbital-lunar`
- 各ケース: warmup 10回、5サンプルの中央値
- 地点: 創作赤星暦は緯度35度・経度0度、地球月baselineは既存の天文東京
- 入力: 創作赤星暦はepoch `0`、地球月baselineは2024-03-20

## 結果

| ケース                                        | 回数 | 中央値合計 |     1回平均 |
| --------------------------------------------- | ---: | ---------: | ----------: |
| 創作衛星 `lunarEquatorial`                    | 1000 |   1.326 ms | 0.001326 ms |
| 創作衛星 `lunarHorizontal`                    | 1000 |   1.510 ms | 0.001510 ms |
| 創作衛星 `lunarEvents`（月出・月没・南中）    |  200 |  15.966 ms | 0.079832 ms |
| 創作衛星 `lunarPhaseEvent`（朔）              |  200 |  16.568 ms | 0.082840 ms |
| 創作赤星太陰太陽暦 `lunisolar`（cache hit）   |  200 |   0.057 ms | 0.000286 ms |
| 創作赤星太陰太陽暦 `lunisolar`（cache clear） |   20 |  60.908 ms | 3.045379 ms |
| 創作赤星太陰太陽暦 `to_tempos`                |  200 |   1.664 ms | 0.008319 ms |
| 創作赤星太陰太陽暦 `format`                   |  200 |   2.801 ms | 0.014006 ms |
| 地球月 `lunarEvents` baseline                 |  200 |  73.770 ms | 0.368849 ms |

### 解釈

- 創作衛星の月出入りは、地球月の約`0.367ms/回`に対して約`0.087ms/回`で、約4.2倍軽い。
- 創作衛星の朔望イベントは約`0.084ms/回`で、月出入りと同程度。
- 最適化前の初回太陰太陽暦解決は約`7.02ms/回`だったが、曖昧候補がない場合の
  安定性拡張窓を省略し、約`3.05ms/回`へ低下した。複数月の朔・中気探索自体は
  依然として追加機能の主なコストである。
- 太陰太陽暦はcache hit後に約`0.00028ms/回`まで下がる。連続表示や同一月のformatでは初回コストを繰り返さない。
- `to_tempos` と `format` はそれぞれ約`0.009ms`、`0.011ms`で、通常の表示更新に対して過大ではない。

## 再測定

```sh
bun run perf:orbital-lunar
```

ベンチマーク本体は [`scripts/perf-orbital-lunar.js`](../scripts/perf-orbital-lunar.js) にある。
`redLunisolarCold` は内部cacheを各回で消去して、初回探索コストを測定する。

## 最適化内容

`constrained-nominal` でも、初期探索窓のすべての朔イベントが一つのcivil day候補へ
確定している場合、中央境界の選択肢は探索窓を拡張しても増えない。この場合だけ
太陽年単位の安定性拡張を省略する。曖昧候補、制約違反、同点経路がある場合は従来どおり
拡張確認を行う。合成specで初期イベント22回だけが呼ばれることを固定している。

創作赤星のcold中央値:

- 最適化前: `7.016075ms/回`
- 最適化後: `3.045379ms/回`
- 削減率: 約`56.6%`

## 朔探索の初期ブラケット最適化

相対朔の `lunarPhaseEvent()` では、`near` における位相差と `P/1024` 先の位相差から
局所傾きを推定し、`near - f/slope` を根の予測値として使う。予測値の `±P/32` を
符号変化付きブラケットとして検証してから、従来と同じ二分探索を行う。

次の条件を満たさない場合は、従来の64分割scanへ戻る。

- `near` 前後の局所傾きが有限かつ同符号である
- 予測根と検証後の根が `near` の `±P/4` 内にある
- 予測ブラケットの両端で符号変化を確認できる
- 二分探索後の位相残差が許容範囲内にある

この `±P/4` 制限は、任意の `LongitudeOrbitalModel` で予測根が別周期の根に
置き換わる可能性を抑えるための安全弁である。局所条件や最近傍性を確認できない
モデルでは高速経路を採用しない。

追加測定（同じ arm64/macOS/Bun 条件、2026-07-31）では、20件の異なる時刻で
太陰太陽暦をcold解決したとき、朔 resolver 560回中547回（`97.7%`）が高速経路を
採用した。

| ケース                          | 変更前の記録 | ブラケット導入後 |
| ------------------------------- | -----------: | ---------------: |
| 創作赤星 `lunisolar` cold中央値 |    `3.045ms` |        `1.431ms` |

これはcold暦全体で約`53%`の短縮に相当する。epoch `near=0` の単発朔ベンチマークは
実際の根が `near` から遠く、`±P/4` ガードでfallbackするため、単体の朔イベント
測定だけでは改善が現れない。暦計算のように、前回の候補境界に近い `near` を連続して
渡す呼び出しで効果が大きい。

## 複数 principal term の全窓列挙

### 測定方法

- 測定日時: 2026-10-12
- CPU architecture: `arm64`
- macOS: `15.6`
- Bun: `1.2.16`
- Node.js: `v22.12.0`
- コマンド: `bun run perf:orbital-lunar`
- 入力: `GregorianAstronomical` は `2024年3月20日`、`JupiterObserved` は epoch `0`
- 各 timing case: warmup 10回、5サンプルの中央値
- cold: sample ごとに20回、各回 `_lunisolar_cache` を消去してから `lunisolar()` を解決
- cache hit: 事前 warmup 後、同じ日時を200回解決

`GregorianAstronomical` と `JupiterObserved` の `solar_phase` 呼び出し数は、timing
とは別に計測する。各暦で cache を消して cold 解決を1回行い、同じ日時でもう1回呼んで
cache-hit 数を数える間だけ `FancyDate.solar_phase` を wrap し、直後に元の method を
復元する。resolver の計測・wrapper は timing sample 内では実行しない。

### 結果

| 暦                      | 全窓化前の `solar_phase` 回数 | 全窓化後 cold / cache-hit |              呼び出し削減 |
| ----------------------- | ----------------------------: | ------------------------: | ------------------------: |
| `GregorianAstronomical` |               444 (`37 × 12`) |                    53 / 0 |    88.1%減、約8.4倍少ない |
| `JupiterObserved`       |         138,060 (`531 × 260`) |                   922 / 0 | 99.33%減、約149.7倍少ない |

全窓化前の呼び出し数と timing は、同一 machine で親が取った比較 baseline。今回の
resolver 数は実測値であり、月数×phase 数の推定値をテスト定数にはしていない。実測数には
各 phase の seed、選択区間に入るまでの hop、および終端を越える最初の resolver 結果も
含まれるため、「phase 数 + 区間内 event 数」という概算とは少し差がある。
事前の概算（地球約50回、木星約800回）に対し、地球は53回、木星は922回だった。地球は
概算に近く、木星の差分は seed と区間端をまたぐ実測 hop を含む。script は推定値を
assertion にせず、この暦・入力での実回数を出力する。

| 暦                      | 親測定の post-step-6 cold | 親測定の pre-step-6 cold | 今回 cold 中央値 | 今回 cache-hit 中央値 |
| ----------------------- | ------------------------: | -----------------------: | ---------------: | --------------------: |
| `GregorianAstronomical` |                13.6955 ms |                7.6696 ms |    1.35994 ms/回 |        0.000160 ms/回 |
| `JupiterObserved`       |                 1.1197 ms |                0.5540 ms |   0.246165 ms/回 |        0.000154 ms/回 |

今回の5サンプル合計時間（ms）:

```text
GregorianAstronomical cold (各sample 20回): [27.198792, 27.490791, 27.330917, 26.613458, 26.797208]
GregorianAstronomical cache hit (各sample 200回): [0.032459, 0.031958, 0.031625, 0.031792, 0.031917]
JupiterObserved cold (各sample 20回): [6.421834, 5.313, 4.923291, 3.97825, 3.950666]
JupiterObserved cache hit (各sample 200回): [0.030792, 0.030291, 0.030167, 0.116959, 0.032875]
```

同一 machine の以前の cache-hit 記録は約65nsだったが、今回の script は暦ごとの
`lunisolar()` 呼び出し全体を測って約154–160ns/回となった。timing path の違い・小さな
値の計測揺れがあるため cache-hit 時間は直接比較しない。cache-hit 中の
`solar_phase` 呼び出しが0回であることは、別計測で確認した。

全窓列挙後は、今回の cold median でも親の post-step-6 baseline より
`GregorianAstronomical` は約90.1%、`JupiterObserved` は約78.0%短かった。ただし安定した
受け入れ基準は resolver 呼び出し数の削減とし、実時間の優劣は runtime・機械・測定条件に
依存する参考値として扱う。

再測定コマンドは従来どおり `bun run perf:orbital-lunar`。
